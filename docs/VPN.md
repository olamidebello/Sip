# Account VPN

WireGuard runs on the SIP host, UDP 51820, interface wg-olamide, IPv4 subnet 10.77.0.0/24. The installer refuses an overlapping route. Up to 253 accounts share this address pool. Each account gets one peer, suitable for one device at a time. Provisioning is idempotent on account login; administrator disable persists across subsequent logins.

In My VPN, download the private configuration, import into the WireGuard client, approve device permission, and enable the tunnel. Android always-on VPN can reconnect independently of website login. Browser JavaScript cannot start a system VPN; this release does not implement a native VpnService or silently change system settings. Full IPv4 Internet traffic routes through the server. IPv6 is captured in the client configuration and not forwarded by the server. DNS uses 1.1.1.1; tunnel MTU is 1280. VPN changes the public source IP and is not proof of physical location. GPS/location policy still applies.

Administrator > VPN management controls per-workspace availability and automatic provisioning, per-user enable/disable, rotation, and last handshake. A recent handshake is evidence of tunnel traffic, not a guarantee of audio. Profiles and keys live in a root-only SQLite database at /var/lib/olamide/vpn/accounts.sqlite3; server keys and bridge token in /etc/olamide/vpn/server.json. Back these up privately. The Docker API reaches a Unix socket using supplemental group 20001; no new control TCP port is published. Private setups are only returned to their account owner. Admin lists never return private keys.

The broker reconciles active platform users at least every 15 seconds plus request processing time using the existing private switch bridge. Suspended users and disabled tenants are omitted. Bridge failure removes all currently authorized peers until synchronization succeeds. Logging out of the website does not disable a separately running device VPN. Admin disable removes the server peer. Rotate requires importing the new client setup.

The installer creates its own nftables tables olamide_vpn and olamide_vpn_nat, plus named accept rules in the existing olamide_guard table when present. No global ruleset flush. VPN clients cannot reach private destinations or host management services; public HTTP/HTTPS DNAT and detected SIP/RTP media are permitted. Other firewall products require manual integration; active UFW/firewalld cause installation to stop. The existing firewall's generic planning command refuses tunnels: manage this dedicated VPN through its own scripts and keep its network service ordered after olamide-firewall. Do not reapply a generic firewall without checking VPN rules.

Service checks and syntax tests do not prove an end-to-end tunnel. After install, import a profile on a phone, check handshake and bidirectional traffic, web access, and two-way call audio. A provider firewall must also allow UDP 51820. WireGuard uses UDP; it is not TURN/TLS and does not bypass a network blocking UDP. TURN remains a separate requirement for browser fallback.

Emergency recovery from an existing public SSH session: stop olamide-vpn-agent, stop wg-quick@wg-olamide, disable both if removing service, then run /usr/local/lib/olamide-vpn/rollback-vpn-network.py. Remove or disable olamide-vpn-network.service so rules do not return at boot. This does not flush Docker rules. The installer preserves pre-deployment source/images/configs; restore those from its private backup if reverting the GUI/API integration. IPv4 forwarding is restored automatically on a failed first install; do not turn it off manually on a Docker host without checking prior state.
