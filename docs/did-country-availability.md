# Provider DID availability by country and area

Billing > Find available numbers by country and area queries enabled provider inventories through the authenticated read-only `/api/numbers/availability` endpoint. It shows actual E.164 numbers grouped by provider, a checked time, loaded count and provider total only where supplied. The country selector supports ISO country codes; it does not promise that every provider has coverage in every country.

Flowroute uses `iso_country`, a US/Canada state/province when supplied, international `starts_with`, and bounded offset pages. Twilio uses the selected country's Local inventory, US/Canada `InRegion`, international `Contains` prefix and bounded pages. This initial panel searches Local Twilio numbers; Mobile and TollFree inventory remain separate capabilities. DIDWW resolves its country ID from ISO code and optionally a region ID, then queries actual `available_dids`. Its reported `total_count` is displayed for unmodified country/region queries. Prefix searches filter the provider's broader contains results, so their total is intentionally unknown. Searches never follow arbitrary pagination URLs.

For non-US/Canada Flowroute/Twilio searches, leave region blank and use the full international number prefix to narrow an area. Unsupported region filters report unavailable rather than returning unfiltered numbers. DIDWW can resolve region names or two-letter abbreviations. SmoothDID searches are limited to its known Nigerian Kwara/Ilorin inventory and use the existing group/user/geofence eligibility handler; at most 50 results are shown and the prefix can be refined.

Billing permission and current service-location access are required. External provider queries also enforce provider lifecycle/service state and geographic provider access with the bound session. SmoothDID keeps its own existing group location controls. Failed/disabled/unconfigured provider searches are unavailable results, never a misleading zero-stock count. Unsupported custom providers need an inventory adapter; their registration alone is insufficient.

Selecting Flowroute/DIDWW or SmoothDID numbers continues in the existing shop, where prices, eligibility and availability are rechecked. Selection does not reserve, charge or allocate a number. Twilio results clearly offer setup requirements because its automated purchase adapter is not implemented. No new purchase or billing endpoint is introduced by this read-only search.

The cumulative Ansible playbook first installs the single sign-in/create-account update and checks the shared authentication schema, then backs up and builds the inventory backend/UI. No inventory cache or additional database tables are required. Existing credentials stay server-side and searches are not publicly cacheable. Local tests use mocked provider responses; actual account inventory and geographic filtering still need production acceptance after installation.
