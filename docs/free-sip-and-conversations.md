# Free internal calling and conversation controls

Registration creates an active user and a SIP account awaiting switch provisioning. No plan is needed for internal calls after provisioning. The dialer authorizes each outgoing call with `/api/softphone/authorize` before sending an INVITE. Registered SIP users in the same active tenant are eligible; users in other tenants are denied. Unknown local identities are denied. External destinations, including valid telephone numbers routed through the local SIP domain, require an active subscription to an active plan belonging to the caller's tenant. Subscription selection and unpaid invoices do not grant external calling. Existing carrier, geographic, credit and fraud restrictions still apply. External SMS sending also requires an active subscription.

The API check protects the application dialer. Arbitrary SIP clients require the updated `OLAMIDE_CALL` switch route. The database migration creates the read-only `olamide_sip_call_access` view; the root-local credential setup grants SELECT on that view. The `sip-accounts.yml` commissioning playbook requires the reviewed subscriber profile to invoke `OLAMIDE_REGISTER` followed immediately by `OLAMIDE_CALL` and to load `sqlops`. The call route fails closed on database failure and reevaluates subscription state on each initial INVITE. Trusted carrier inbound traffic needs a separately authenticated ingress configuration; this subscriber-only include rejects unauthenticated initial INVITEs. Do not add a general carrier bypass based on untrusted From or destination headers. Validate the full switch bundle using `kamailio -c` and test SIP registration, internal calls, external rejection, subscribed external calls, cancellation, tenant isolation, and legitimate carrier inbound routing before cutover. Application deployment alone does not install the switch configuration.

Account messages now support replies, edits by the sender, removal by the sender, six emoji reactions, read receipts, typing indicators, search within the latest 100 messages, blocking, mute and archive preferences, and selecting a contact's SIP address in the dialer. The browser polls an open visible conversation every five seconds. Read means a visible authenticated conversation fetched the message; it does not prove a human read it. Sent means the server accepted it; carrier delivery is unrelated. Muting suppresses the new-message announcement; archived conversations are hidden from the selector until Show archived conversations is enabled. Blocking prevents new messages in either direction while preserving existing history. Message sending is serialized with block changes and capped at 60 per minute per sender. All mutations bind identity to the authenticated session, enforce tenant boundaries and require the current user to participate. Message bodies are rendered as text.

Messages and reaction metadata are stored on the application server and are not end-to-end encrypted. Removed message bodies are replaced by a tombstone in the live database; previous backups may still contain historical content. This release does not implement all WhatsApp features: encrypted group chats, media/file sharing, voice notes, 24-hour statuses, channels, linked devices, background mobile notifications and WhatsApp interoperability are not included. Existing meetings and SIP calling remain separate application features.

Validation: API tests cover free/paid/cross-tenant call authorization, session ownership, blocked sends, invalid replies, sender-only edits/removal and safe conversation controls. Web tests exercise text rendering, reply/edit/reaction mutations, receipts, search and contact calls. The full GUI navigation suite remains applicable. Production MySQL and a commissioned Kamailio runtime are needed for the migration and actual media/ingress checks.
